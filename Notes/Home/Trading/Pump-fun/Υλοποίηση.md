# Rule v2 για υλοποίηση
Υλοποίησέ το **ακριβώς ως intent-based rule με σταθερή απόφαση στα 45 ms**. Δεν χρησιμοποιεί probabilities και δεν περιμένει Yellowstone-confirmed αγορές.
Το επιλεγμένο development candidate είναι:
```text
exactly_2_external_wallets
+ both_ready_before_2ms
+ buyer1_total_below_1.5_SOL
+ each_wallet_has_exact_quote_intent
+ 0.75 <= external_total / creator_total < 2.0
```
Αυτό είναι το `v1_both_exact_quote_ratio_gte_0_75`, το οποίο έδωσε 77,27% win rate στα 22 OOS development trades. Δεν έχει ακόμη περάσει νέο ανεξάρτητο holdout.

---
## 1. Σταθερές παραμέτρους
```yaml
entry_rule_v2:
  enabled: true
  decision_window_ms: 45
  buyers_ready_before_ms: 2
  creator_buy_min_sol: 0.5
  creator_buy_max_sol: 5.0
  required_external_wallets: 2
  buyer1_max_total_sol: 1.5
  external_creator_ratio_min: 0.75
  external_creator_ratio_max: 2.0
  require_each_wallet_has_exact_quote_intent: true
  buy_sol: 0.075
exit:
  take_profit_net_pct: 2.0
  stop_loss_net_pct: -20.0
  max_hold_ms: 15000
```
Τα όρια είναι:

|Συνθήκη|Σύγκριση|
|---|---|
|Creator buy|`>= 0.5` και `<= 5.0 SOL`|
|Δεύτερος buyer ready|`< 2 ms`|
|Buyer 1 total|`< 1.5 SOL`|
|External/creator ratio|`>= 0.75` και `< 2.0`|
|External wallets|`== 2` στα 45 ms|
Οι συνθήκες αυτές είναι κλειδωμένες και στον validator v2.

---
# 2. Χρονική βάση
Για κάθε νέο mint:
```text
T0 = τοπικός monotonic χρόνος όταν παραλήφθηκε το create
deadline = T0 + 45 ms
```
Χρησιμοποίησε monotonic durations και όχι wall-clock timestamps για τις συγκρίσεις.
Η τελική απόφαση γίνεται **μία φορά στα 45 ms**. Ο timer:
- ξεκινά στο create,
- δεν επανεκκινείται όταν εμφανίζεται buyer,
- δεν παρατείνεται,
- δεν γίνεται accept μόλις εμφανιστεί ο δεύτερος buyer.
```text
0 ms        create
<2 ms       πρέπει να έχουν εμφανιστεί ήδη 2 unique external wallets
45 ms       τελικός έλεγχος όλων των συνθηκών
```

---
# 3. Ποια intents θεωρούνται ορατά
Μέχρι το deadline συμπεριλαμβάνονται:
1. Όλα τα instructions που έχουν την ίδια signature με το create.
2. Μεταγενέστερα intents με:
```text
createReceivedAt < intentReceivedAt <= createReceivedAt + 45 ms
```
Τα same-signature instructions θεωρούνται ότι έγιναν ορατά μαζί με το create και για το timing παίρνουν delay `0 ms`. Αυτή ήταν ακριβώς η συμπεριφορά του replay.

---
# 4. Ταξινόμηση intents
## Creator initial buy
Ένα buy είναι creator initial buy μόνο όταν:
```go
intent.Kind == Buy &&
intent.Signature == create.Signature &&
intent.User == create.Creator
```
Δεν πρέπει να χαρακτηρίσεις ως creator initial buy μια μεταγενέστερη αγορά του creator σε άλλη transaction.
## External buy
Ένα buy είναι external όταν:
```go
intent.Kind == Buy &&
intent.User != create.Creator
```
Ο creator δεν μετρά ποτέ στους δύο external buyers. Η ταξινόμηση αυτή χρησιμοποιήθηκε και στο amount analysis.
## Creator sell
Reject όταν μέχρι το deadline υπάρχει:
```go
intent.Kind == Sell &&
intent.User == create.Creator
```
Το tested rule απέρριπτε **creator sell**, όχι υποχρεωτικά sell οποιουδήποτε άλλου wallet.

---
# 5. State ανά mint
Πρότεινα να κρατήσεις κάτι αντίστοιχο:
```go
type BuyerState struct {
    Wallet                  PublicKey
    FirstSeenAt             time.Time
    FirstSequence           uint64
    TotalQuoteLamports      uint64
    FirstIntentQuoteLamports uint64
    IntentCount             int
    ExactQuoteIntentCount   int
    ExactTokenIntentCount   int
}
type EntryCandidateV2 struct {
    Mint            PublicKey
    Creator         PublicKey
    CreateSignature Signature
    CreateSlot      uint64
    CreatedAt time.Time
    Deadline  time.Time
    IsMayhem bool
    CreatorBuyTotalLamports uint64
    CreatorBuyUnpriced      bool
    CreatorSellVisible      bool
    Buyers map[PublicKey]*BuyerState
    ExternalUnpriced bool
    TerminalRejected bool
    RejectReason     string
    Timer *time.Timer
}
```
Όλα τα events του ίδιου mint πρέπει να περνούν σειριακά από έναν mint worker ή να προστατεύονται από lock. Η αξιολόγηση στα 45 ms δεν πρέπει να τρέξει ταυτόχρονα με ενημέρωση intent.

---
# 6. Aggregation των buyers
Οι buyers είναι **unique wallets**, όχι αριθμός intents.
Παράδειγμα:
```text
Wallet A: 3 buy intents
Wallet B: 1 buy intent
```
Αυτό μετρά ως:
```text
2 external buyers
4 external buy intents
```
Για κάθε wallet αποθηκεύεις:
```text
first_seen_at
συνολικό SOL όλων των buy intents του wallet μέχρι τα 45 ms
αριθμό exact-quote intents
αριθμό exact-token intents
```
Το replay ομαδοποιούσε τα external buy intents ανά wallet και άθροιζε το κανονικοποιημένο `user_quote_amount` κάθε intent.

---
# 7. Buyer 1 και buyer 2
Στα 45 ms ταξινόμησε τα δύο wallets με σειρά:
```text
1. first_seen_at
2. event sequence
3. wallet address ως τελικό deterministic tie-break
```
Ο πρώτος είναι `buyer1` και ο δεύτερος `buyer2`.
```go
sort.Slice(buyers, func(i, j int) bool {
    if !buyers[i].FirstSeenAt.Equal(buyers[j].FirstSeenAt) {
        return buyers[i].FirstSeenAt.Before(buyers[j].FirstSeenAt)
    }
    if buyers[i].FirstSequence != buyers[j].FirstSequence {
        return buyers[i].FirstSequence < buyers[j].FirstSequence
    }
    return buyers[i].Wallet.String() < buyers[j].Wallet.String()
})
```

---
# 8. Συνθήκη «both buyers ready < 2 ms»
Δεν είναι το gap μεταξύ buyer1 και buyer2.
Είναι:
```go
buyer2.FirstSeenAt.Sub(create.CreatedAt) < 2*time.Millisecond
```
Επειδή ο buyer2 είναι ο δεύτερος χρονικά, αυτό αποδεικνύει ότι και οι δύο buyers είχαν εμφανιστεί πριν από τα 2 ms.
```text
Buyer 1: 0.4 ms
Buyer 2: 1.7 ms
PASS
Buyer 1: 0.4 ms
Buyer 2: 2.0 ms
FAIL
Buyer 1: 0.4 ms
Buyer 2: 2.1 ms
FAIL
```
Το όριο είναι αυστηρά `<2 ms`, όχι `<=2 ms`.

---
# 9. Συνθήκη «exactly 2 external buyers»
Στα 45 ms πρέπει να ισχύει:
```go
len(candidate.Buyers) == 2
```
Δεν κάνουμε accept μόλις εμφανιστεί ο δεύτερος.
Παράδειγμα:
```text
0.4 ms: wallet A
1.2 ms: wallet B
20 ms:  wallet C
45 ms:  evaluate
```
Αποτέλεσμα:
```text
FAIL — external_wallet_count = 3
```
Ο τρίτος buyer μπορεί να προκαλέσει terminal reject αμέσως, επειδή μέχρι το deadline ο αριθμός unique wallets δεν μπορεί να ξαναγίνει δύο.
Repeated intents από τα ίδια δύο wallets δεν αυξάνουν το unique count.

---
# 10. Buyer 1 κάτω από 1,5 SOL
Η συνθήκη αφορά το **συνολικό ποσό όλων των intents του πρώτου wallet μέχρι τα 45 ms**:
```go
buyer1.TotalQuoteLamports < 1_500_000_000
```
Όχι μόνο το πρώτο intent του buyer1.
Παράδειγμα:
```text
Buyer 1 intent 1: 0.8 SOL
Buyer 1 intent 2: 0.6 SOL
Buyer 1 total:    1.4 SOL
PASS
```
```text
Buyer 1 intent 1: 1.0 SOL
Buyer 1 intent 2: 0.5 SOL
Buyer 1 total:    1.5 SOL
FAIL
```
Το `1.5 SOL` ακριβώς απορρίπτεται.

---
# 11. Exact-quote συνθήκη
Το replay θεωρούσε intent `exact_quote` όταν:
```go
intent.InputMode == ExactQuote ||
intent.SpendableQuoteLamports > 0
```
Σε αυτή την περίπτωση το ποσό προκύπτει από:
```go
spendable := intent.SpendableQuoteLamports
if spendable == 0 {
    spendable = intent.LimitLamports
}
```
Η ταξινόμηση αυτή υπάρχει στο amount analysis.
## Ακριβής tested semantics
Για να αντιγράψεις το rule όπως αξιολογήθηκε, απαίτησε:
```go
buyer1.ExactQuoteIntentCount >= 1 &&
buyer2.ExactQuoteIntentCount >= 1
```
Ο validator v2 ελέγχει ακριβώς `>=1` για κάθε wallet.
Αυτό σημαίνει ότι, αν ένα wallet έχει δύο intents:
```text
1 exact-quote
1 exact-token
```
το tested rule το δέχεται, επειδή έχει τουλάχιστον ένα exact-quote intent.
Μην το αλλάξεις σε:
```go
ExactTokenIntentCount == 0
```
γιατί αυτό θα ήταν αυστηρότερο και διαφορετικό rule.

---
# 12. Υπολογισμός ποσών
Μην χρησιμοποιήσεις απλώς το raw `limit_lamports` για όλα τα intents.
Χρησιμοποίησε την ίδια normalization με το replay:
```go
quoteAmount, err := QuoteIntentAgainstSequentialIntentCurve(intent)
```
Για κάθε intent:
- exact-quote: εκτέλεση ως συγκεκριμένο spendable quote,
- exact-token: υπολογισμός του απαιτούμενου SOL πάνω στην προσωρινή sequential intent curve,
- μετά ενημέρωση της προσωρινής curve πριν αξιολογηθεί το επόμενο intent.
Αν κάποιο creator ή external intent δεν μπορεί να μετατραπεί αξιόπιστα σε ποσό:
```text
REJECT
```
Το replay απέρριπτε περιπτώσεις με unpriced creator ή external intents, ώστε το ratio να μην υπολογίζεται από ελλιπή ποσά.

---
# 13. Creator buy
Υπολόγισε:
```go
creatorBuyTotal := sum(
    normalizedQuoteAmount
    for same-signature buys by creator
)
```
Απαίτησε:
```go
0.5 SOL <= creatorBuyTotal &&
creatorBuyTotal <= 5.0 SOL
```
Αν:
- δεν υπάρχει creator,
- δεν υπάρχει creator initial buy,
- το ποσό δεν μπορεί να υπολογιστεί,
- το ποσό είναι εκτός ορίων,
τότε reject.

# 14. External/creator ratio
Υπολόγισε το σύνολο όλων των buy intents των δύο external wallets μέχρι τα 45 ms:
```go
externalTotal :=
    buyer1.TotalQuoteLamports +
    buyer2.TotalQuoteLamports
```
Μετά:
```go
ratio := float64(externalTotal) / float64(creatorBuyTotal)
```
Απαίτησε:
```go
ratio >= 0.75 &&
ratio < 2.0
```
Παραδείγματα:

|Ratio|Αποτέλεσμα|
|--:|---|
|0,7499|Reject|
|0,7500|Accept|
|1,5000|Accept|
|1,9999|Accept|
|2,0000|Reject|
Το ratio χρησιμοποιεί τα συνολικά amounts των δύο wallets, όχι μόνο τα πρώτα τους intents.

# 15. Πλήρης τελική αξιολόγηση
```go
func EvaluateEntryRuleV2(c *EntryCandidateV2, now time.Time) Decision {
    if now.Before(c.Deadline) {
        return Decision{Status: Pending}
    }
    if c.TerminalRejected {
        return Reject(c.RejectReason)
    }
    if c.IsMayhem {
        return Reject("mayhem")
    }
    if c.Creator.IsZero() {
        return Reject("missing_creator")
    }
    if c.CreatorBuyUnpriced {
        return Reject("incomplete_creator_amount")
    }
    if c.ExternalUnpriced {
        return Reject("incomplete_external_amount")
    }
    if c.CreatorBuyTotalLamports < 500_000_000 {
        return Reject("creator_buy_below_min")
    }
    if c.CreatorBuyTotalLamports > 5_000_000_000 {
        return Reject("creator_buy_above_max")
    }
    if c.CreatorSellVisible {
        return Reject("creator_sell_visible")
    }
    if len(c.Buyers) != 2 {
        return Reject("external_wallet_count_mismatch")
    }
    buyers := OrderedBuyers(c.Buyers)
    buyer1 := buyers[0]
    buyer2 := buyers[1]
    readyDelay := buyer2.FirstSeenAt.Sub(c.CreatedAt)
    if readyDelay >= 2*time.Millisecond {
        return Reject("two_buyers_not_ready_before_2ms")
    }
    if buyer1.TotalQuoteLamports >= 1_500_000_000 {
        return Reject("buyer1_total_at_or_above_max")
    }
    if buyer1.ExactQuoteIntentCount < 1 {
        return Reject("buyer1_missing_exact_quote")
    }
    if buyer2.ExactQuoteIntentCount < 1 {
        return Reject("buyer2_missing_exact_quote")
    }
    externalTotal :=
        buyer1.TotalQuoteLamports +
        buyer2.TotalQuoteLamports
    ratio := float64(externalTotal) /
        float64(c.CreatorBuyTotalLamports)
    if ratio < 0.75 {
        return Reject("external_creator_ratio_below_min")
    }
    if ratio >= 2.0 {
        return Reject("external_creator_ratio_at_or_above_max")
    }
    return Decision{
        Status: Accept,
        Rule:   "intent_entry_v2",
    }
}
```

# 16. Πότε υποβάλλεται η αγορά
Όταν το rule περάσει στα 45 ms:
1. Πάρε την πιο πρόσφατη authoritative Yellowstone curve.
2. Μην προσθέσεις τα Deshred intents στην execution curve.
3. Κάνε fresh quote για αγορά `0.075 SOL`.
4. Build/sign/send αμέσως.
5. Μην περιμένεις τεχνητά για το slot `N+1`.
Το replay υπέθεσε ότι η αγορά landed στη θέση `0` του `N+1`. Αυτό είναι assumption του replay, όχι condition που μπορεί να εγγυηθεί ο live κώδικας. Το live πρέπει να καταγράφει:
```text
create_slot
decision_slot
submit_slot
landed_slot
create_to_decision_us
decision_to_submit_us
decision_to_landed_us
```
Η είσοδος πρέπει να βασίζεται στην authoritative curve· τα pending intents χρησιμοποιούνται μόνο για BUY/SKIP classification.

---
# 17. Exit rule
Μετά από επιβεβαιωμένη αγορά:
```text
buy amount: 0.075 SOL
net TP: +2%
net SL: -20%
max hold: 15 seconds
```
Το PnL πρέπει να είναι execution-aware:
```go
entryDebit :=
    actualCurveDebit +
    buyProtocolFee +
    buyCreatorFee +
    buyNetworkFee +
    buyTip +
    attributableEntryCosts
projectedSellNet :=
    projectedCurveProceeds -
    sellProtocolFee -
    sellCreatorFee -
    expectedSellNetworkFee -
    expectedSellTip
netPnL := projectedSellNet - entryDebit
netPnLPct := 100 * float64(netPnL) / float64(entryDebit)
```
Triggers:
```go
if netPnLPct >= 2.0 {
    Exit("take_profit")
}
if netPnLPct <= -20.0 {
    Exit("stop_loss")
}
if time.Since(position.OpenedAt) >= 15*time.Second {
    Exit("max_hold")
}
```
Τα 50 ms ήταν **replay assumption για το landing latency της πώλησης**. Δεν πρέπει να προσθέσεις τεχνητό sleep 50 ms. Στο live submit της πώλησης πρέπει να γίνει αμέσως μετά το trigger.

## Κρίσιμη προειδοποίηση
Αυτό που υλοποιείς είναι:
```text
Deshred intent-based selection
+
authoritative Yellowstone curve για execution
```
Δεν είναι:
```text
Yellowstone-confirmed buyer rule
```
και δεν είναι:
```text
probability-weighted intent rule
```
Οποιαδήποτε αλλαγή σε αυτά τα δύο σημεία δημιουργεί διαφορετική στρατηγική και τα προηγούμενα replay αποτελέσματα δεν μεταφέρονται αυτόματα.

Όχι, **όχι για να αναπαράγεις ακριβώς το rule που δοκιμάσαμε**.
### Η σωστή διάκριση
#### Το `create` για το timing και την επιλογή
Πρέπει να είναι το **Deshred `create_v2` intent/event**.
Από αυτό ξεκινούν:
```text
T0 = received_at του Deshred create
decision deadline = T0 + 45 ms
```
Επίσης από την ίδια Deshred transaction παίρνουμε:
- mint,
- bonding curve,
- creator,
- token program,
- mayhem flag,
- creator initial buy,
- same-signature external buy intents.
Αυτή ήταν η ακριβής βάση του replay: ξεκινούσε από κάθε Deshred Pump `create_v2` και θεωρούσε creator buy αυτό που υπήρχε στην ίδια create transaction.
#### Το state για την πραγματική αγορά
Πριν γίνει submit, πρέπει να υπάρχει **authoritative Yellowstone curve account** για το ίδιο mint/curve.
Δηλαδή:
```text
Deshred create:
candidate creation και χρονόμετρο
Yellowstone curve:
απόδειξη ότι το token/curve υπάρχει
και authoritative reserves για το buy quote
```
Η αρχιτεκτονική της εφαρμογής ήδη διαχωρίζει το Deshred ως predictive stream από το Yellowstone ως authoritative account και transaction state.
### Προτεινόμενη ροή
```text
1. Έρχεται Deshred create
2. Δημιουργείται candidate
3. Ξεκινά αμέσως το σταθερό παράθυρο των 45 ms
4. Συλλέγονται τα Deshred buyer intents
5. Στα 45 ms αξιολογείται το intent rule
6. Πριν από build/submit απαιτείται fresh authoritative Yellowstone curve
7. Γίνεται fresh quote πάνω στην authoritative curve
8. Submit BUY
```
### Τι πρέπει να επιβεβαιώσεις πριν από το submit
Το Yellowstone snapshot πρέπει να είναι:
```go
snapshot.Mint == candidate.Mint
snapshot.Curve == candidate.Curve
snapshot.Generation == currentYellowstoneGeneration
snapshot.Initialized
!snapshot.Complete
snapshot.IsFresh()
```
Όπου είναι διαθέσιμα authoritative metadata, έλεγξε επίσης:
```go
snapshot.Creator == candidate.Creator
snapshot.IsMayhem == candidate.IsMayhem
```
Σε οποιοδήποτε mismatch:
```text
REJECT — create_authoritative_mismatch
```
Αν μέχρι το execution deadline δεν υπάρχει authoritative curve:
```text
REJECT — authoritative_curve_unavailable
```
Για live δεν θα χρησιμοποιούσα predicted curve fallback.
### Τι δεν πρέπει να κάνεις
Μην περιμένεις πρώτα το Yellowstone-confirmed create και μετά ξεκινήσεις τα 45 ms:
```text
Λάθος για το tested rule:
Yellowstone create arrives
→ start 45 ms timer
```
Αυτό:
- θα μετακινήσει χρονικά το παράθυρο,
- μπορεί να συμπεριλάβει διαφορετικά intents,
- μπορεί να αλλάξει ποιος θεωρείται buyer1 και buyer2,
- και αποτελεί διαφορετική στρατηγική από αυτή που κάναμε replay.
Επίσης μην επανεκκινείς τον timer όταν φτάσει το authoritative curve.
### Συνοπτικά

|Στοιχείο|Πηγή|
|---|---|
|Έναρξη candidate|Deshred create|
|Έναρξη 45 ms|Deshred create receive time|
|Creator initial buy|Deshred, ίδια signature με create|
|External buyers|Deshred intents|
|Rule v2 BUY/SKIP|Deshred intent state στα 45 ms|
|Απόδειξη ότι υπάρχει η curve|Yellowstone account|
|Reserves για buy quote|Yellowstone authoritative curve|
|Επιβεβαίωση δικής μας αγοράς|Yellowstone transaction|
Άρα:
> **Το create δεν χρειάζεται να είναι authoritative για να ξεκινήσει το rule. Πριν όμως στείλεις πραγματική αγορά, πρέπει να έχει επιβεβαιωθεί έμμεσα ή άμεσα από authoritative Yellowstone state ότι το συγκεκριμένο mint και curve υπάρχουν και ταιριάζουν.**


Ναι, **για το rule που κάναμε replay ισχύει ακριβώς αυτό**:

|Στοιχείο|Πηγή|
|---|---|
|`create`|Deshred `create_v2`|
|creator initial buy|Deshred buy intent στην ίδια signature με το create|
|external buyers|Deshred buy intents|
|creator sell|Deshred sell intent|
|buyer1 / buyer2|Σειρά εμφάνισης των Deshred intents|
|ποσά και ratio|Εκτιμώμενα από τα Deshred intents|
|`exact_quote`|Ιδιότητα του Deshred intent|
|χρονική αρχή `T0`|Τοπικό `received_at` του Deshred create|
|χρόνος buyer|Deshred intent `received_at − create received_at`|
|τελικός έλεγχος|`T0 + 45 ms`|
Για intents στην ίδια signature με το create, το replay τα θεωρούσε ορατά στο `T0`, δηλαδή delay `0 ms`.
Άρα:
```text
Deshred create στα 0 ms
Deshred buyer A στα 0,4 ms
Deshred buyer B στα 1,3 ms
τελικός έλεγχος στα 45 ms
```
Οι χρόνοι είναι χρόνοι **παραλαβής από το Deshred stream**, όχι χρόνοι επιβεβαίωσης στο blockchain.
Η σημαντική διάκριση είναι:
```text
Deshred intents → επιλογή BUY/SKIP και timing
Yellowstone → authoritative curve για quote και επιβεβαίωση πραγματικών executions
```
Επομένως οι δύο buyers του rule μπορεί τελικά:
- να εκτελεστούν,
- να αποτύχουν,
- να μην προσγειωθούν,
- ή να προσγειωθούν με διαφορετικό ordering.
Το rule δεν απαιτεί να έχουν επιβεβαιωθεί. Χρησιμοποιεί το μοτίβο των intents ως πρώιμο στατιστικό σήμα. Πριν από τη δική μας αγορά, όμως, το quote πρέπει να γίνεται πάνω στην authoritative Yellowstone curve και όχι πάνω στην curve που προβλέπεται από τα intents.
